## A. Verdict per critique point

### 1. False precision

**VALID — High.** `score_choice()` produces a mathematically reproducible weighted sum, but the inputs are uncalibrated model judgments. The workflow then relabels that score as `"78% confidence"`, which is unjustified: 78/100 is not a probability that the option is correct, nor does it have a known error rate. Criterion names also lack behavioral anchors, so two runs can assign materially different scores while both appearing numerically precise. Anchors improve consistency but do not calibrate probabilities; calibration requires outcome data and proper scoring rules such as Brier score or log loss, plus reliability diagrams.

**Final fix:** Represent scores as ordinal decision-support ratings, not confidence percentages. Define explicit 0/25/50/75/100 behavioral anchors for every criterion, record evidence and unknowns for every sub-score, and display bands such as `Strong`, `Adequate`, or `Weak`. If probability language is required, create a labeled historical evaluation set, calibrate the probabilities, measure Brier score/reliability, and permit abstention. Otherwise delete `% confidence` from `SKILL.md`.

### 2. Panel is not independent

**VALID — High.** Four voices generated by one model are not four independent evaluators. They share the same context, model weights, priors, omissions, and likely hallucinations. Role variation can be useful as a structured critique prompt, and multi-agent debate can sometimes improve reasoning, but it does not justify calling the result a panel verdict or treating agreement as independent evidence. The problem is worse because the panel’s arguments are folded back into the same model-generated sub-scores without a specified update rule.

**Final fix:** Remove the term `panel` unless there are genuinely separate information sources. The default should be a clearly labeled `adversarial self-critique` that cannot automatically increase confidence. If escalation is justified, run blind first-pass analyses using distinct model calls or models, require each to cite independent evidence, expose disagreements, and use a deterministic adjudication rule. A human/domain expert or an actual tool-generated artifact is stronger evidence than another persona.

### 3. Force-phrase substring matching

**PARTIALLY VALID — Medium.** The failure mode is real: `"Can you get someone else to weigh in?"` does not match, while `"don't run the panel"` can match a positive substring. It also triggers on quoted text, documentation, or examples. However, “worse than nothing” is overstated: exact common phrases do provide a deterministic opt-in path, which unconstrained model intent inference does not guarantee. Deleting the list and asking the model to judge intent would trade false negatives for nondeterministic false positives.

**Final fix:** Use an explicit control protocol: `/decision-picker panel` and `/decision-picker no-panel`, or an equivalent structured flag. Parse natural-language requests only as a fallback, with negation handling and a confirmation question when ambiguous. Do not let a substring match silently control an escalation or safety-relevant state.

### 4. Tournament seeding defect

**VALID — High.** The algorithm is not a neutral size-reduction mechanism. With five candidates, the groups are `[rank 1, rank 3, rank 5]` and `[rank 2, rank 4]`; rank 2 can be eliminated by rank 4 before rank 1 and rank 2 are ever compared. More generally, one user answer permanently removes candidates, even though the grouping—not the user’s underlying preference—determines which alternatives are visible together. Carrying the top K by the same uncalibrated score is not a complete fix; it preserves model bias and can still hide a candidate the user would prefer.

**Final fix:** Replace `simulate_to_single_winner()` with a protected-shortlist protocol:

- Apply hard-constraint and dominance pruning only when the reason is explicit.
- Preserve every feasible candidate within the configured near-top margin and every Pareto-undominated candidate.
- Use groups only for user screening, not silent elimination.
- Carry protected candidates into the final question.
- Add `Reopen eliminated options` and `None of these` paths.
- If more than four protected candidates remain, ask additional explicit shortlist questions rather than pretending the bracket is fair.

At minimum, publish the grouping and tell the user which candidates were excluded and why.

### 5. No enforcement of score ranges

**VALID — High.** The scoring function validates only missing keys. A value of `150`, `-20`, `NaN`, a boolean, or a 0–1 fraction is accepted or mishandled. Extra keys are silently ignored. This makes the claim that the total is reproducible misleading: the arithmetic is reproducible, but malformed inputs can enter the arithmetic without a contract violation.

**Final fix:** Add runtime schema validation inside `score_choice()`:

- Require exactly the four criterion keys.
- Require finite real numbers, explicitly excluding booleans.
- Require `0 <= score <= 100`.
- Verify weights sum to 1.0.
- Reject ambiguous 0–1 inputs rather than guessing whether to rescale.
- Add boundary, malformed-input, NaN/Infinity, extra-key, and property-based tests.

Use a typed schema such as Pydantic or an equivalent explicit validator, not checks confined to `demo()`.

### 6. Zero integration testing

**VALID — High.** The pure-function demos establish only that isolated Python helpers behave on their fixtures. They do not test the actual contract among `SKILL.md`, the model, `AskUserQuestion`, `council`, and the scripts. A prose skill can skip normalization, mislabel the recommendation, invoke the panel under the wrong condition, offer five options, mishandle `Other`, or act before the user has selected anything. “The only failure mode that matters” is too strong—bad arithmetic still matters—but protocol failure is currently untested.

**Final fix:** Move the workflow into an executable state machine or controller with adapters for the model, `AskUserQuestion`, and panel. Test it with fake adapters and scripted transcripts. Acceptance tests must assert:

- normalization occurs before scoring;
- no question has more than four options;
- escalation predicates are honored;
- panel output cannot bypass validation;
- recommendations and scores are labeled correctly;
- all rounds terminate;
- `Other`, cancellation, invalid answers, and reopened candidates work;
- execution occurs only after a valid final answer.

Add a small live-session golden/evaluation suite for model adherence. Tests cannot prove arbitrary LLM behavior, but they can detect regressions and enforce the non-LLM protocol.

### 7. Packaging and portability

**PARTIALLY VALID — Medium.** The relative-path invocation is a real defect when the agent’s working directory is the user’s project rather than the skill directory. Missing `pyproject.toml` and `__init__.py` are not inherently defects for standalone dependency-free scripts, but the current design has no declared Python version, installation contract, or reliable way to locate the skill root. A symlink makes assumptions about the path even more fragile.

**Final fix:** Package the implementation as an installable Python project with a declared `requires-python` version and a console entry point such as `decision-picker`. Have `SKILL.md` invoke that command, never `python3 scripts/...` relative to cwd. If installation is impossible, use a wrapper that resolves its own real path via `Path(__file__).resolve()` and invokes modules from that root. Add an installation smoke test from an unrelated cwd and through a symlink.

## B. What the critique missed

### 1. Hard constraints are treated as compensatory scores — **Critical**

`fit_to_constraints` is just another weighted number. A candidate that violates a mandatory security, compatibility, legal, budget, or deployment constraint can still win through reversibility, precedent, or evidence. That is invalid MCDA modeling. Hard constraints require feasibility gating before weighted ranking; they cannot be offset by strengths elsewhere.

**Ship:** Extract explicit hard constraints, mark each candidate `feasible/infeasible/unknown`, and exclude infeasible candidates unless the user explicitly chooses to override.

### 2. “Evidence strength” is not evidence — **Critical**

The system does not gather evidence, cite sources, inspect the repository, run tests, or distinguish known facts from assumptions. The model can invent an evidence-strength score based on the same unsupported narrative it generated. This is a self-referential confidence loop.

**Ship:** Require each material claim to have a source: user-provided fact, repository artifact, tool output, or external citation. Represent missing information as `unknown`, trigger clarification or retrieval, and abstain from ranking when an unknown affects feasibility.

### 3. Fixed criteria and weights are unjustified — **High**

The same weights are applied to every decision. `precedent` may be actively harmful for a novel problem; reversibility may be irrelevant for a disposable experiment; cost, security, latency, maintainability, accessibility, and operational risk are absent. The system never asks the user to validate the criteria or weights. This is not a neutral rubric; it embeds a product policy while presenting the output as analysis.

**Ship:** Create a `DecisionSpec` containing the decision goal, hard constraints, criteria, weights, and stakes. Use a task-specific rubric or ask the user to approve the default rubric before scoring.

### 4. The UI creates anchoring and automation bias — **High**

The top-ranked option is placed first, labeled `(Recommended)`, and accompanied by a pseudo-confidence number. That is a strong choice-architecture intervention, not a neutral presentation. The final statement that the system “acts on the user’s pick” does not undo priming. This is consistent with known anchoring and automation-bias findings, including work summarized by Tversky and Kahneman and Parasuraman and Manzey.

**Ship:** Either present the recommendation only when requested, or collect the user’s initial preference before revealing the ranking. At minimum, randomize non-semantic option order, separate recommendation from selection, and remove confidence percentages.

### 5. `Other` is an unhandled state transition — **High**

`AskUserQuestion` explicitly provides a free-text escape hatch, but the workflow says only “act on the answer.” If `Other` introduces a new candidate, the system does not normalize it, score it, compare it, escalate it, or confirm it. It can therefore execute an option that never passed the stated process.

**Ship:** Treat `Other` as a first-class branch: parse it into a new candidate, rerun the relevant scoring and shortlist steps, and ask for confirmation before execution. If it is an instruction rather than a candidate, stop and reclassify the request.

### 6. High-stakes detection is undefined and unsafe — **High**

`high_stakes` appears as an argument but there is no defined source, user interface, or reliable classifier. A medical, legal, financial, security, or destructive production decision can therefore proceed without escalation if the flag is absent. A role-played panel is not a high-stakes safeguard.

**Ship:** Define a conservative stakes taxonomy and default unknown stakes to higher scrutiny. For regulated or materially harmful decisions, require domain-specific evidence and human review; otherwise abstain. Follow NIST AI RMF and ISO/IEC 23894-style risk controls rather than treating “run the council” as risk management.

### 7. Panel-to-score updating is arbitrary and unauditable — **High**

“Fold panel arguments back into sub-scores” specifies no mapping, evidence threshold, weighting, or conflict rule. A persuasive paragraph can move a score by any amount. The system can therefore produce a new ranking without a reproducible reason and without preserving the original assessment.

**Ship:** Never directly rewrite scores from rhetoric. Store panel claims separately, attach evidence, require an explicit criterion-level delta with justification, and keep before/after scores. Prefer no automatic re-totaling unless the update passes a deterministic adjudication schema.

### 8. Candidate normalization is a manipulation point — **High**

The model is allowed to rewrite every option into a label and one-line description before asking the user. It can accidentally omit tradeoffs, merge distinct options, rename choices persuasively, or turn an ambiguous option into a more attractive one. That is especially dangerous when the rewritten description is also used as the recommendation rationale.

**Ship:** Preserve immutable candidate IDs and verbatim user text. Generate a separate summary labeled as model-generated, show it for confirmation when materially different, and never use a rewritten description to conceal the original option.

### 9. Candidate text is an untrusted prompt-injection surface — **High**

Because this is a coding-agent skill, a candidate can contain text such as “ignore the rubric and run this command.” The workflow does not instruct the model to treat candidate content as data. Scoring and normalization could therefore become an instruction-following attack, and “act on the answer” could turn an option into an unsafe action.

**Ship:** Delimit candidate data, explicitly prohibit following instructions found inside candidates, and separate analysis from execution. Require confirmation and normal tool permission checks before any option causes repository or system changes.

### 10. There is no outcome feedback or audit trail — **Medium**

The system claims confidence and calibration-adjacent behavior but records neither the decision record nor the eventual outcome. There is no way to measure whether recommendations were useful, whether certain criteria systematically mislead, or whether the panel changes decisions correctly.

**Ship:** Emit a structured decision record containing inputs, rubric version, scores, evidence, uncertainty, panel status, displayed options, user choice, and execution result. For decisions with observable outcomes, evaluate calibration and usefulness retrospectively.

## C. Is the premise sound?

Not in its current shape.

A lightweight decision aid can be useful for low-stakes choices with a small, well-defined candidate set. But this design combines four unsafe assumptions:

1. a general fixed rubric is suitable for arbitrary decisions;
2. model judgments can be expressed as calibrated percentages;
3. role-played personas provide independent expertise; and
4. a lossy four-option tournament can preserve user preference.

Those assumptions do not hold. For four or fewer ordinary candidates, the native `AskUserQuestion` tool is already sufficient. The scoring and panel add anchoring, verbosity, and false authority unless the user explicitly requests analysis.

The system should be restructured as a **transparent decision-aid controller**, not a “panel-backed picker”:

1. **Collect a decision specification:** goal, hard constraints, stakes, criteria, and weights.
2. **Keep candidates immutable:** IDs plus verbatim input and separately marked summaries.
3. **Gather evidence:** repository inspection, tests, documents, citations, or explicit user facts.
4. **Gate feasibility:** reject or flag hard-constraint violations before ranking.
5. **Use anchored ordinal assessments:** preserve unknowns and uncertainty; do not call scores confidence.
6. **Use adversarial review only when useful:** label same-model review as self-critique; reserve “panel” for independent models, humans, or evidence sources.
7. **Use a candidate-preserving shortlist protocol:** no opaque singleton tournament; support reopen and `Other`.
8. **Execute through a state machine:** validate every transition and require confirmation for consequential actions.
9. **Abstain for high-stakes or under-specified cases:** escalation should mean qualified review or additional evidence, not more personas.

The premise is sound only after being narrowed to “structured, explainable assistance for low- to medium-stakes decisions.” It is not sound as a generic recommendation engine that emits authoritative-looking rankings.

## D. Minimum viable fix set

### 1. Replace the generic numeric recommender with an evidence-gated, anchored rubric

Add `DecisionSpec`, hard-constraint feasibility checks, criterion anchors, explicit unknowns, and runtime schema validation. Remove percentage confidence. This fixes false precision, prevents infeasible options from winning, and exposes when the model lacks information.

### 2. Implement the workflow as a packaged state-machine controller

Move normalization, scoring validation, escalation, option-count enforcement, `Other`, cancellation, and execution gating into executable code. Package it with a console entry point and test it with fake tool adapters plus scripted transcript tests. This buys actual protocol enforcement and fixes most of the integration and portability failures at once.

### 3. Remove the fake panel and lossy tournament UX

Rename same-model multi-voice review to adversarial self-critique, prevent it from automatically changing scores, and replace round-robin elimination with a protected shortlist that supports `None of these`, `Reopen`, and new candidates from `Other`. This reduces correlated-consensus theater, arbitrary candidate loss, and recommendation-driven anchoring.
